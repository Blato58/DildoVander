# ESP32-S3 suitcase firmware

The ESP32-S3 owns the conversation, local safety gates and calibrated physical
sequence. It talks directly to the backend; the phone is an observer/controller,
not a cloud relay. Production uses ESP-IDF 6.1 through the pinned PlatformIO
platform 7.1.3. Arduino support is retired.

GPT Live `gpt-live-1` is primary; GPT Realtime 2.1 `gpt-realtime-2.1` is an explicit
alternative. Both use authenticated persistent device WSS and 24 kHz mono PCM.
The ESP is half duplex: software capture gating is not verified acoustic AEC.
Profile B has a residual admitted DMA tail and no instantaneous amplifier mute.
No provider text can directly command an actuator.

## Build

The root project forwards to this same six-environment project. From the
repository root:

```powershell
pio run -e production
pio run -e diag-board-memory -e diag-hardware-service -e diag-network-service -e diag-pca9685-logic -e diag-servo-bench
```

Builds do not flash a board, provision credentials, execute diagnostics or
establish hardware acceptance. Never run simultaneous `.pio`/CMake writers in
one checkout. Generated `.pio`, SDK and build files are not source. Diagnostic
images are separately flashable and are excluded from production OTA packages.
Disabled example service settings must be generated by the diagnostic's tracked
generator before its build; do not replace personal calibration or credentials.

## Servo bench and confirmed pulse range

The standalone [servo-bench diagnostic](diagnostics/servo-bench/README.md)
controls free, unloaded servos over local USB. The owner physically
confirmed **600–2300 us for all six servos on 2026-10-21**; `cal` advertises
and enforces that range. The narrow `pulse` test remains 1400–1600 us.
This evidence does not establish measured angles, installed mechanism limits
or production calibration. Stop writes PWM FULL_OFF and does not remove 5 V.
The browser panel also supports local music analysis and synchronized dance
with Play, Pause and Stop. Its continuous 25 Hz dance has no 500 ms pulse
cycle; select channels 0–5 and assign each its own bass, mid, treble, onset,
energy or phrase trajectory. It requires explicit operator preparation and
adequate power for the selected servos. Physical synchronization and
multi-servo load acceptance remain separate from software validation.
## Provision, inspect and recover

Device credentials live in NVS, not the image. Provider keys stay on the backend.
Use the physically confirmed USB network service only with explicit service
execution authority; [journal establishment](docs/journal-establishment.md)
documents factory, legacy and interrupted-resume modes. Established data loss,
wrong device binding, malformed inventories or uncertain commits fail closed.
Normal boot never creates or rebinds an identity or restamps an old operation.

Every boot requires inspection before motion. Verify the actual board/profile,
calibration, power switch and unobstructed compartments, then perform the
existing physical inspection/recovery action. Positions are calibrated timed
commands, not measured position feedback. GPIO2 drives PCA OE directly; the
purchased green power switch separately disconnects actuator power. Software
cannot prove that the switch, voltage or mechanism is safe.

Stop invalidates volatile action authority immediately. An authenticated current
local Stop latches OE off before waiting for the normal control pass. A stale
callback cannot re-enable it. Inspection recovery clears the latch only at the
same Stop epoch. A failed/unknown durable write requires authoritative reopen;
never retry a physical action merely because its acknowledgement was lost.

[OTA health](docs/ota-boot-health.md) separates local image/configuration health
from inspection and motion readiness. A healthy passive image can confirm with
outputs disabled and without a hotspot, IP or provider. Inspection remains
mandatory afterward. OTA identity and slot rollback behavior require bench
validation; a build is not proof of rollback or safe power interruption.

## Runtime and durable operations

`production/main.cpp` constructs dependencies and starts owners.
[Bounded runtime](docs/bounded-runtime.md) describes the sole actuator/control
owner, absolute 10 ms scheduling, immediate Stop gate and separate service work.
[Storage ownership](docs/runtime-storage-owner.md) covers asynchronous intent,
reservation, completion, evidence and recovery. No control pass commits NVS or
waits for TLS, downloads or a storage worker.

A journal entry's original epoch/UUID/slot/fingerprint is immutable. Durable
intent precedes movement; completion proof follows return and fresh timing
validation. [Epoch history](docs/journal-epochs.md) and committed inventories
retain required evidence across bounded compaction. Thirty-two entries limit a
retained window, not lifetime operations; a wholly pinned backlog refuses new
motion rather than evicting proof. Scoped mode requires explicit established
identity and complete committed-source reconciliation.

[Device media](docs/device-backend-media.md) and
[asynchronous playback](docs/asynchronous-media-owner.md) describe bounded
queues, exact credits and consumed/drained frontiers. Uncertain uploads,
malformed/out-of-order frames, expired admission or broken continuity terminate
explicitly. Reconnect never replays microphone audio or a physical command.
The [native simulator](simulator/native/README.md) shares this session/playback
orchestration over a bounded backend WSS bridge; fake providers remain explicit.

[Lab carrier](docs/lab-voice-carrier.md) describes the capability-gated private
test ticket. Its token is RAM-only; test-origin physical journal history is
durable and is excluded from production keepsake publication. A scoped Lab Stop
must exactly match its active hashed context; mismatch has no global fallback.

## Local protocol and diagnostics

The pinned local TLS channel supports offline manual control independently of
WAN/AI. [Typed refusals](docs/local-control-refusals.md) keep authenticated,
well-formed sessions open for busy, stale, recovery and unsupported outcomes.
Retired Text requests explicitly require an engine upgrade. Old `/opening`,
`/turns`, polling and per-batch ESP media transports are absent from production.
Shared correlation/proposal codecs and explicit compatibility rejections remain.

[Runtime diagnostics](docs/runtime-diagnostics.md) are bounded, redacted and
capability-negotiated. They distinguish network, authentication, trusted time,
inspection/motion, queue/frontier, heap/PSRAM, stack, storage and scheduling facts.
No ticket, bearer, guest audio/transcript/image or private payload belongs in a
technical log. Targets of 20 ms software Stop and 50 ms application-level audio
cancel require workload/board measurement. SDK bus-fault recovery can exceed a
nominal control period; actual maxima and overruns are reported, not hidden.

## Verification and evidence

Run the [reproducible software checks and fault matrix](docs/redesign-acceptance.md).
They include production plus five diagnostic builds, real shared journal/control
lifecycle crash tests, local real-socket transport faults and at least four hours
of simulated no-provider media/show cycling. Keep the exact source, commands,
exits, seed, buffers and timing assumptions with each result.

The [exact-build bench checklist](docs/firmware-reliability-bench.md) separates
prepared checks from unrun board, iPhone hotspot, microphone/speaker, camera,
actuator/power and OTA-slot tests. Simulated I/O, loopback WS, unsigned iOS builds
and static RAM size do not establish physical latency, position, acoustic tail,
NVS power-cut behavior or peak activated heap/stack acceptance.

Historical implementation slices are [archived separately](README-history.md).


## Customer Bluetooth start (protocol 1)

The existing protocomm BLE lifecycle owns both service and customer modes. The
customer service UUID is `B97A7F10-70E8-4B98-9DCC-40D66395C822`; its single
read/write characteristic is `B97AFF55-70E8-4B98-9DCC-40D66395C822`. Service
provisioning retains its bounded PoP-authenticated window and UUID ending C821.
Explicit backend customer enablement switches the same lifecycle to the public
customer service; this never exposes provisioning endpoints and does not require
a service PoP. Audio hardware and an enabled voice mode must also be available.

Each complete JSON request and reply is at most 512 bytes. Requests carry
`v:1` and `op:challenge|start|status|end`. Start additionally carries an opaque
account ticket and UUID `operationId`; status may carry that UUID to recover its
session ID. Challenge registration is authenticated by the device backend token
and bound to its boot, catalog, generation and operation epoch. A changed runtime
snapshot requires a new challenge. The backend owns ticket authorization and
conversation context; the device redeems outside the BLE callback and uses the
returned conversation ID before entering the existing voice workflow.

Customer admission runs under the existing control-owner urgent fence and refuses
manual leases, maintenance, recovery, dance and unavailable snapshots. The voice
reservation also excludes service voice starts. Phone disconnect does not cancel
voice. BLE `end` is a status hint only: the signed-in account requests its own end
through HTTPS and the device polls that exact session and boot. Service Stop
retains its existing operator authority.

A timed-out redemption holds the reservation while the authenticated device
status reconciles the original operation. If accepted IDs are recovered without
an active local voice, the device reports failure for that exact session so the
backend closes it before permitting another visitor. An unresolved operation
stays recovering. Boot reconciliation sends `device-idle` only after the control
owner has published a safe idle snapshot; it never infers safety from phone
connection state. The backend must only retire old-boot leases in that request.

The once-per-second authenticated status poll includes optional `bootId` and
`ready=true|false` query fields on `/v1/customer-sessions/device`. Readiness is
sampled from the existing control-owner idle fence, voice/reservation exclusion,
boot reconciliation and current challenge snapshot. This advisory observation
neither starts a conversation nor releases a lease. The backend accepts presence
only for the registered boot and an unexpired challenge, and forgets in-memory
presence after restart. Observations ten seconds old become unknown. Older
clients may omit both fields and receive the unchanged status response; their
token-only poll supplies no readiness evidence. Ticket issuance, consent,
proximity and actual lease acquisition remain separate checks.

`pio run -e production` verifies compilation. Existing host harnesses cover BLE
lifecycle isolation, adopted conversation IDs and owner admission. These checks
do not prove iPhone Bluetooth, ESP32 radio/audio coexistence, actual physical
position, provider personalization, or customer end latency on hardware.
